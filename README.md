# Cardcraft · проверяемые карточки КИП

Локальный AI-помощник для подготовки черновиков карточек B2B-магазина. Принимает JSON, обращается к OpenAI API или локальному Ollama API и отдаёт JSON или Markdown: SEO-заголовок, описание на 800–1200 символов, характеристики, поисковые запросы и блок для менеджера.

**Ключевое решение:** LLM выбирает порядок характеристик, фрагмент назначения и редакционный сценарий, а технические значения переносит код из исходных данных. У каждой характеристики есть JSON Pointer на источник. Новые значения из ответа модели не принимаются.

Python 3.10+ · без runtime-зависимостей · CLI + HTTP API · тесты без API-ключа.

**По умолчанию — OpenAI.** Ollama подключается только явно через `--provider ollama` как дополнительная локальная опция. `--demo` — отдельный режим без вызова модели. Ошибка одного провайдера не приводит к переключению на другой.

## Проверить за минуту

Из корня репозитория:

```bash
python3 -m cardcraft examples/input/manometer.json --demo --format markdown
python3 -m unittest discover -s tests -v
```

Установка пакета не обязательна. При желании:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
cardcraft examples/input/manometer.json --demo
```

`--demo` — явный offline-режим. Его результат содержит `meta.mode: "demo"` и предупреждение. После ошибки настоящего API сервис **не** переключается на деморежим.

## Основной вариант: OpenAI API

Самый простой способ — интерактивная проверка:

```bash
python3 scripts/check_live.py
```

Создайте ключ на [странице API keys](https://platform.openai.com/api-keys), запустите команду в обычном терминале и вставьте ключ в скрытый запрос. Значение не отображается, не сохраняется в файлы или историю команд. Скрипт делает два реальных API-запроса (с возможными повторами при временной ошибке), расходующих лимит API-аккаунта. Результаты сохраняются отдельно в `output/live/`: JSON с источниками и Markdown. Оба сообщения `OK` и код выхода 0 означают успешное завершение, но назначение и предупреждения нужно прочитать вручную.

Если `OPENAI_API_KEY` уже задан в окружении, скрипт использует его без запроса. Обычный CLI тоже читает эту переменную. `.env` автоматически не загружается. Для macOS zsh можно ввести ключ в текущую сессию так:

```zsh
read -rs 'OPENAI_API_KEY?OpenAI API key: '
export OPENAI_API_KEY
python3 -m cardcraft examples/input/manometer.json --format markdown -o output/live/manometer.md
unset OPENAI_API_KEY
```

Запускайте команды в том же терминале: переменная не переносится в уже открытые другие процессы. Для изменения модели перед запуском задайте `export OPENAI_MODEL=gpt-4o-mini`. Подробнее: [проверка с API-ключом](docs/api-check.md).

Модель настраивается через `OPENAI_MODEL`; нужна поддержка Chat Completions и Structured Outputs. Доступность модели зависит от аккаунта. `.env.example` описывает переменные, но автоматической загрузки `.env` нет. Ключ не попадает в код, результат или логи. `.env` исключён из Git.

Данные товара отправляются в OpenAI только при выбранном провайдере OpenAI без `--demo`. При `--provider ollama` запрос направляется локальному серверу. Вызывается фиксированный HTTPS endpoint, поэтому конфигурация не может незаметно перенаправить ключ на сторонний сервер.

**Статус проверки:** OpenAI-адаптер протестирован на подменённом HTTP-транспорте, включая формат запроса и обработку ошибок. Настоящий OpenAI-запрос остановился на HTTP 429 (`credit_balance_exhausted`); успешная генерация через OpenAI не подтверждена. Дополнительный Ollama-провайдер проверен настоящими запросами на двух примерах. [Сохранённые live-результаты](examples/ollama) отделены от [offline-demo](examples/output).

## Дополнительная опция: локальная модель через Ollama

Если Ollama уже запущен и модель скачана:

```bash
ollama list
python3 -m cardcraft examples/input/manometer.json --provider ollama --format markdown
python3 -m cardcraft examples/input/demo-incomplete.json --provider ollama -o output/ollama/demo-incomplete.json
```

По умолчанию используется `llama3.2:3b`. Другую **локальную** модель можно выбрать через `OLLAMA_MODEL`. Приложение не скачивает модели самостоятельно. При отсутствии модели сначала установите её средствами Ollama. Запуск без оплаты внешнего API использует ресурсы вашего компьютера.

Для HTTP-сервиса: `python3 -m cardcraft --serve --provider ollama`. Провайдер обращается к `http://127.0.0.1:11434/api/chat`, передаёт JSON Schema в `format`, не передаёт OpenAI-ключ и не переключается на облако при ошибке. Имена моделей с `cloud` отклоняются. Таймаут ответа — 180 секунд, автоматических повторов нет. `meta.mode: live` здесь означает настоящий вызов локальной модели; её имя видно в `meta.model`.

[Structured Outputs в Ollama](https://docs.ollama.com/capabilities/structured-outputs) ограничивает структуру; собственный валидатор дополнительно проверяет ID. Для небольшой модели используется компактный английский промпт с примером JSON-ответа, версия `grounded-plan-ollama-v2` записана в `meta.prompt_version`. Русские исходные данные передаются без перевода. Качество выбора цитаты всё равно нужно проверять; два успешных примера не доказывают качество на всех паспортах.

## Формат входа

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления...",
  "required_specs": ["диапазон измерений", "класс точности", "присоединение"]
}
```

Обязателен только непустой `name`. Значения характеристик — строки с единицами измерения; пустая строка и `null` означают отсутствие данных. Числа вместо строк отклоняются: нельзя угадать единицы. Максимум 40 характеристик, 300 символов на значение, 12 000 на описание, 64 КБ на JSON. Неизвестные поля и повторяющиеся JSON-ключи отклоняются, чтобы не скрывать опечатки и потери данных.

`required_specs` — необязательный список полей, важных для этой категории/задачи. Отсутствующие значения попадут в `missing_fields`, а в характеристиках появится «данных нет». Имена сравниваются точно. Без такого списка нельзя знать все необходимые параметры произвольного прибора; сервис отмечает только известные пропуски и общую нехватку сведений.

Пробелы по краям значений удаляются; сами значения и единицы не пересчитываются. Некорректный JSON и отсутствие названия возвращают понятную ошибку до обращения к LLM.

## Локальный HTTP API

```bash
python3 -m cardcraft --serve --demo
# Для реального API уберите --demo и задайте OPENAI_API_KEY.
```

В другом терминале:

```bash
curl http://127.0.0.1:8080/health
curl -sS http://127.0.0.1:8080/generate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/input/manometer.json
```

`POST /generate` принимает тот же объект, что CLI. Ответ — JSON. `GET /health` проверяет только локальный процесс, не доступность/оплату LLM API. Порт меняется через `--port 8081`. Сервер слушает только loopback; веб-интерфейса и публичного деплоя нет.

Ошибки имеют вид:

```json
{"error":{"code":"missing_name","message":"Укажите name: без названия нельзя сформировать карточку."}}
```

HTTP: 400 — JSON/запрос, 413 — размер, 415 — Content-Type, 422 — входные данные/отказ модели, 502 — некорректный ответ или доступ к LLM, 503 — недоступность API/нет ключа. CLI возвращает код 2, пишет ошибку в stderr, успешный результат — в stdout либо `--output`. При неуспехе новый файл результата не записывается.

## Что проверяется автоматически

- SEO-заголовок не длиннее 70 символов; описание — 800–1200 символов с пробелами и переводами строк, по `len(str)` до Markdown-экранирования.
- 3–5 уникальных поисковых запросов из названия, производителя и подтверждённого диапазона измерений. Это кандидаты, не исследование поисковой частотности.
- Все непустые входные характеристики присутствуют в результате; пустые явно отмечены.
- План модели содержит только разрешённые ключи, сценарии и существующие ID. Пропуск, повтор или выдуманный ID отклоняется.
- `evidence`, `characteristics.source` и `commercial.task_source` позволяют проверить происхождение использованных данных.
- `meta` содержит режим, модель, версию промпта, редакционный план и SHA-256 нормализованного входа. Хеш связывает результат с данными, но не доказывает достоверность паспорта.

`quality.status` всегда `needs_review`: даже структурно корректный текст остаётся черновиком для человека. Слишком длинное название сокращается с явным предупреждением. Спорные фрагменты сохраняются в `review_items`; модель не «исправляет» исходные значения.

## Промпт и архитектура

Полный промпт и JSON Schema находятся в [cardcraft/prompts.py](cardcraft/prompts.py), обоснование — в [docs/decisions.md](docs/decisions.md).

```text
JSON → валидация → факты/фрагменты с ID → LLM: редакционный план
                                            ↓
JSON/Markdown ← проверка длины ← сборка ← проверка ID и схемы
```

- `domain.py`: входной контракт, источники, проверка плана.
- `ollama.py`: локальный REST-вызов, схема с допустимыми ID и обработка ошибок Ollama.
- `provider.py`: выбор провайдера, REST-вызов OpenAI, явный demo-provider, таймаут 30 секунд на попытку; до трёх попыток с паузами 1 и 2 секунды только для сетевых ошибок, 429 и временных 5xx.
- `editorial.py`: абзацы по конкретным параметрам, аудитория из назначения, опорные факты и вопросы заказчику; версия редакционных правил записывается в результат.
- `render.py`: сборка карточки, признаки отсутствующих данных, ссылки на источники, Markdown-экспорт.
- `__main__.py`, `server.py`: тонкие CLI/HTTP адаптеры.

Используется [Structured Outputs из официальной документации OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs). JSON Schema ограничивает форму ответа, а наша проверка ID дополнительно ограничивает его содержимое. Сырые ответы ошибок провайдера не показываются пользователю и не логируются.

## Тесты и ограничения

```bash
python3 -m unittest discover -s tests -v
python3 scripts/check_acceptance.py
```

41 тест: CLI и настоящий локальный HTTP round trip, повреждённый JSON, дубли ключей, пустые поля, происхождение значений, 200 сгенерированных граничных входов, неизвестные ID, prompt injection, Markdown escaping, отказ/обрезка ответа, 401, 429, сетевые ошибки. Дополнительно проверены различия аудитории и вопросов для двух товаров, отсутствие общей добивки у манометра и исключение спорных характеристик из SEO/commercial. В CI настроены Python 3.10, 3.12, 3.13; локально проверен Python 3.10. Тесты не требуют интернета и денег, но HTTP-тестам нужен loopback-порт.

Сознательные ограничения MVP:

1. Текст собирается из исходных данных и правил для конкретных параметров (диапазон, точность, присоединение, корпус, питание, интерфейс). Для неизвестных полей и скудного входа сохраняются общие рекомендации; это отмечается предупреждением, если их два и более. Свободные технические обещания не генерируются. LLM здесь редактор плана, не автор всего текста.
2. Происхождение не равно истинности. В исходном JSON могут быть ошибки, инструкции или конфликтующие данные. Модель может пропустить конфликт или неверно выбрать назначение; сохранение исходных фрагментов не гарантирует семантическую корректность. Публикация требует редактора.
3. Назначение берётся как целое предложение до 320 символов; длинный или неясный фрагмент не пересказывается. Данные из паспорта не превращаются автоматически в новые характеристики `specs`.
4. Нет базы, авторизации, ограничителя нагрузки, массовой обработки и UI. Стандартный HTTP-сервер предназначен только для локального прототипа. Нет жёсткого общего дедлайна для медленно передающего ответ провайдера.
5. Описание 800–1200 символов трактуется как текст карточки по ТЗ, а не короткий HTML meta description.

Следующие шаги: реальный прогон на размеченном наборе паспортов; отдельная оценка выбора назначения/конфликтов; профили категорий с обязательными полями; extraction-проход с подтверждаемыми цитатами; UI для редактирования и сравнения с источником. Свободную LLM-переформулировку добавлять только после измерения ошибок фактической точности.
