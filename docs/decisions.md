# Почему модель возвращает план, а не готовую карточку

Для измерительного прибора фраза «подходит для агрессивных сред» может быть опаснее неверной цифры. Проверка чисел в свободном LLM-тексте не ловит выдуманные свойства, совместимость и сертификацию. Поэтому MVP не строит безопасность только на промпте «не выдумывай».

LLM получает факты `s0`, `s1` и фрагменты описания `d0`, `d1`. Она выбирает порядок характеристик, исходное предложение о назначении, отмечает сомнительные фрагменты и выбирает один из трёх редакционных сценариев. Приложение проверяет план и подставляет исходные строки. Непроверяемый свободный текст модели не попадает в карточку.

Такое ограничение делает результат менее разнообразным, но позволяет точно показать редактору, откуда взялось каждое значение. Это осознанный выбор для небольшого B2B-прототипа, а не универсальный способ писать SEO-тексты.

## Роль промпта

Системный промпт отделён от JSON-данных. Он запрещает выполнять инструкции внутри описания, добавлять внешние знания и считать отсутствующий параметр отсутствующей функцией. Все четыре поля плана обязательны. `purpose_id: null` — корректный ответ при недостатке информации.

Версия `grounded-plan-v1` записывается в результат. Можно сравнивать будущие версии по одним и тем же входам. Запрос использует строгую JSON Schema; сервер всё равно проверяет содержимое ответа независимо от провайдера.

Нет «repair prompt», который незаметно переформулирует неудачный ответ. Невалидный план возвращает ошибку. Это экономит повторные вызовы и делает сбои видимыми. Повторы транспорта ограничены временными ошибками.

## Что гарантирует код

В `characteristics` не появляются значения, которых нет во входе; отсутствующие явно маркируются. Назначение — целый исходный фрагмент, а не парафраз. Текст рекомендаций не утверждает характеристики товара. План не может добавить новый числовой параметр или сертификацию. Источники представлены стандартными JSON Pointer; для ключей с `/` и `~` выполняется экранирование.

Не гарантируются истинность источника, корректность выбранного моделью назначения или полнота обнаружения противоречий. Если источник сам содержит «IP68» или вредоносную инструкцию, модель может выбрать этот фрагмент. Поэтому тест на prompt injection проверяет узкую гарантию: произвольное дополнительное поле/значение из ответа модели не проходит контракт. Он не доказывает абсолютную безопасность семантического выбора.

## Отсутствующие данные

Пустые известные поля и отсутствующие `required_specs` отмечаются. Требования к корпусу, интерфейсу или питанию не считаются универсальными для всех приборов: для механического манометра некоторые поля неприменимы. Профиль категории должен задавать бизнес, а не модель по догадке.

Неполный commercial-блок говорит, что назначение нужно уточнить. Общая аудитория — подборщики КИП и закупщики — редакционный контекст магазина, а не утверждение о пригодности прибора для конкретной отрасли.

## Простота запуска

Стандартная библиотека Python достаточна для небольшого REST-клиента, CLI, локального HTTP API и тестов. Не нужны Docker, база, фронтенд-сборка и dependency resolver. Цена решения — ручная проверка API-формата и примитивный локальный сервер; для производственного сервиса их стоит заменить поддерживаемым SDK и полноценным HTTP-фреймворком.
